## definition

The method states the intent of the request on the resource: read (GET), create or process (POST), replace (PUT), partially modify (PATCH), delete (DELETE), ask only for the headers (HEAD) or query what is allowed (OPTIONS).

## analogy

A customer card in a filing cabinet: **GET** is reading it, **POST** is handing in a new card so the archive assigns it a number, **PUT** is swapping the whole card for another, **PATCH** is correcting only the phone number with correction fluid, **DELETE** is removing it, **HEAD** is asking whether it exists and when it was modified without taking it out, and **OPTIONS** is asking what you are allowed to do with it.

## problem

Methods tell the whole infrastructure what it can do with the request: caches only store GET, clients automatically retry idempotent ones, and browsers send a preflight depending on the method. Using POST for everything makes you lose caching, safe retries and clarity.

## code:wire

```http
# Estado actual de /v1/clientes/7
{"id":7,"nombre":"Ana Ruiz","email":"ana@mail.co","telefono":"3001112233"}

PUT /v1/clientes/7 HTTP/1.1
Content-Type: application/json

{"nombre":"Ana Ruiz","email":"ana@nuevo.co"}
# → el teléfono se pierde: PUT reemplaza la representación completa

PATCH /v1/clientes/7 HTTP/1.1
Content-Type: application/merge-patch+json

{"email":"ana@nuevo.co"}
# → solo cambia el email; el teléfono queda igual
```

## code:server

```python
class ClienteIn(BaseModel):            # PUT: todos los campos obligatorios
    nombre: str
    email: str
    telefono: str

class ClientePatch(BaseModel):         # PATCH: todos opcionales
    nombre: str | None = None
    email: str | None = None
    telefono: str | None = None

@app.put("/v1/clientes/{id}")
def reemplazar(id: int, data: ClienteIn): ...

@app.patch("/v1/clientes/{id}")
def actualizar(id: int, data: ClientePatch):
    cambios = data.model_dump(exclude_unset=True)   # solo lo que llegó
    ...
```

## bad

```http
POST /v1/clientes/7/eliminar
GET  /v1/clientes/7/borrar        ← un crawler o un prefetch lo ejecuta
POST /v1/actualizarCliente
```

## good

```http
DELETE /v1/clientes/7
PATCH  /v1/clientes/7
PUT    /v1/clientes/7
```

## bridge:typescript

The `OPTIONS` request you see in Network before your `PUT` was not made by you: it is the CORS preflight the browser sends (see [[cors]]). And when you use `fetch` with `method: "PUT"` to edit a half-filled form, you are deleting on the server the fields you did not send, if the backend implements PUT correctly.

## interview

GET fetches a resource without modifying it; POST creates a resource in a collection or triggers processing; PUT completely replaces the representation of the resource at that URI, so the fields you do not send are lost; PATCH applies a partial modification; DELETE removes; HEAD is like GET but without a body, useful to check headers or existence; and OPTIONS describes which methods the resource supports, and it is what the browser uses in the CORS preflight. The key difference between PUT and PATCH is full replacement versus partial change, and that PUT is idempotent by definition while PATCH is not necessarily.

## myths

- Using PUT and PATCH as synonyms. PUT replaces the whole resource; PATCH applies partial changes.
- Believing PUT only updates. With PUT the client can also create a resource at a URI it chooses (`PUT /archivos/foto.png`).
- Thinking DELETE must return the deleted resource. The usual thing is 204 with no body.
