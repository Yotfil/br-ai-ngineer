    Clase y objeto

    La clase es el molde. El objeto es cada cosa concreta que sale del molde, con su propio estado.

    AnalogíaEl formulario en blanco de "Pedido" es la clase. Cada formulario diligenciado por un cliente distinto es un objeto. Todos tienen los mismos campos y cada uno guarda datos diferentes.
    class Pedido:
    def __init__(self, cliente):   # constructor: deja el objeto listo para usarse
        self.cliente = cliente     # estado propio de ESTE objeto
        self.items = []

    def agregar_item(self, precio):   # comportamiento
        self.items.append(precio)

    def total(self):
        return sum(self.items)

p1 = Pedido("Ana")    # un objeto (instancia)
p2 = Pedido("Luis")   # otro objeto: mismo molde, estado independiente
    Pruébalo

    Crea varios pedidos y agrégale ítems a uno solo. Los demás no cambian: cada objeto tiene su propia memoria.

    Ciclo de vida de un objeto

    1. Pedido("Ana")Python reserva memoria para el objeto.
    2. __init__El constructor le pone su estado inicial.
    3. UsoLlamas métodos; el estado cambia.
    4. Sin referenciasYa ninguna variable apunta a él.
    5. RecolectorPython libera la memoria solo.
    Detalle de Pythonself es el this de TypeScript, pero se escribe explícito como primer parámetro de cada método. __init__ equivale a tu constructor().
    Dilo así en la entrevista"Una clase define qué datos y qué comportamiento tiene un tipo de cosa. Un objeto es una instancia concreta de esa clase, con su propio estado en memoria. El constructor garantiza que el objeto nazca en un estado válido."

    Los cuatro pilares

    La pregunta de apertura más común. Cada pilar resuelve un problema distinto.

    Protege

    Encapsulamiento

    El objeto guarda su estado y solo deja cambiarlo por métodos que controlan las reglas.

    Un cajero: no metes la mano en la bóveda, pides un retiro y él valida.Sin él: cualquiera deja el objeto en un estado imposible, como un saldo negativo.
    Simplifica

    Abstracción

    Muestras qué hace algo y escondes cómo lo hace.

    Pagas con el datáfono sin saber qué banco, red ni protocolo hay detrás.Sin ella: quien usa tu clase tiene que conocer todos los detalles internos.
    Reutiliza

    Herencia

    Una clase toma lo que ya tiene otra y agrega o cambia lo suyo. Relación "es un".

    Una cuenta de ahorros es una cuenta bancaria con intereses.Sin ella: copias y pegas el mismo código en clases parecidas.
    Flexibiliza

    Polimorfismo

    El mismo mensaje, enviado a objetos distintos, produce el comportamiento de cada uno.

    Presionas "play" y cada app reproduce a su manera: música, video o podcast.Sin él: cadenas de if tipo == ... por todo el código.
    class CuentaBancaria:
    def __init__(self, saldo):
        self._saldo = saldo              # encapsulamiento: estado protegido

    def retirar(self, monto):            # abstracción: quien llama no ve las reglas
        if monto > self._saldo:
            raise ValueError("Fondos insuficientes")
        self._saldo -= monto

class CuentaAhorros(CuentaBancaria):     # herencia: es una CuentaBancaria
    def retirar(self, monto):            # polimorfismo: misma llamada, otra regla
        if monto > 2_000_000:
            raise ValueError("Tope diario superado")
        super().retirar(monto)

    Dónde lo ves:

    class Pedido:
    # Atributo de clase: un solo diccionario compartido por todos los pedidos.
    # Clave = estado actual. Valor = conjunto (set) de estados a los que puede pasar.
    # El guion bajo inicial avisa: "uso interno, no lo toques desde fuera".
    _TRANSICIONES = {
        "creado":  {"pagado", "cancelado"},      # de creado solo puede ir a estos dos
        "pagado":  {"enviado", "reembolsado"},   # de pagado, a enviado o reembolsado
        "enviado": {"entregado"},                # de enviado, solo a entregado
        # "entregado" no aparece como clave: es un estado final, de ahí no sale
    }

    # Constructor: se ejecuta al escribir Pedido(81)
    def __init__(self, id):
        self.id = id                  # dato público: cualquiera lo puede leer
        self._estado = "creado"       # dato protegido: todo pedido nace en "creado"

    # @property convierte el método en un atributo de solo lectura.
    # Se usa SIN paréntesis: pedido.estado   (no pedido.estado())
    # Como no se define un setter, pedido.estado = "x" lanza AttributeError.
    # Equivale a un `get estado()` en una clase de TypeScript.
    @property
    def estado(self):
        return self._estado           # entrega el valor interno sin dejar cambiarlo

    # Métodos públicos: la única forma de cambiar el estado desde fuera
    def marcar_pagado(self):
        self._cambiar_a("pagado")     # delega en el método interno, que valida

    def marcar_enviado(self):
        self._cambiar_a("enviado")    # misma idea, otro estado destino

    # Método interno (guion bajo): la regla vive aquí, en un solo lugar
    def _cambiar_a(self, nuevo):
        # Busca a qué estados se puede ir desde el estado actual.
        # .get(clave, set()) devuelve un conjunto vacío si la clave no existe
        # (caso "entregado"), en vez de lanzar KeyError.
        permitidos = self._TRANSICIONES.get(self._estado, set())
        if nuevo not in permitidos:   # ¿la transición NO está permitida?
            # raise corta la ejecución y lanza el error (el `throw` de TypeScript)
            raise ValueError(f"No se puede pasar de {self._estado} a {nuevo}")
        self._estado = nuevo          # solo llega aquí si la transición es válida

pedido = Pedido(81)        # crea el objeto; su estado es "creado"
print(pedido.estado)       # imprime "creado": lectura a través de la property
pedido.marcar_enviado()    # ValueError: de "creado" no se puede pasar a "enviado"

    La regla vive en un solo lugar. Sin esto, cada endpoint, tarea programada y script de soporte tendría que acordarse de validarla, y alguno no lo hará.

    # Único método público: lo que el resto del sistema puede pedir (el "qué").
    # `pdf: bytes` y `-> str` son anotaciones de tipo, como en TypeScript:
    # recibe el contenido del archivo en bytes y devuelve un texto (la URL).
    def guardar(self, factura_id, pdf: bytes) -> str:
        ruta = self._ruta(factura_id)            # 1. decide dónde va el archivo
        self._subir_con_reintentos(ruta, pdf)    # 2. lo sube; si falla, reintenta
        return self._url_firmada(ruta)           # 3. devuelve un enlace de descarga

    # De aquí hacia abajo es el "cómo". El guion bajo marca que son internos.
    # Los `...` son un cuerpo vacío: ahí iría el código real de cada paso.

    # Arma la ubicación, por ejemplo "facturas/2026/81.pdf"

    # Habla con el proveedor de archivos y repite el intento si la red falla
    def _subir_con_reintentos(self, ruta, datos): ...

# Si mañana cambias de proveedor, esta línea no cambia.

# Hereda de Exception: por eso se puede

class ErrorDeNegocio(Exception):
    # Atributo de clase: valor por
    # defecto para toda la familia
    codigo_http = 400

    def __init__(self, mensaje):

        # del padre (Exception), como

        self.mensaje = mensaje

# El contrato: "cualquier objeto con un método generar(prompt) que devuelva texto".
# Los `...` indican que no hay implementación: solo se describe la forma.
class ModeloDeLenguaje(Protocol):
    def generar(self, prompt: str) -> str: ...

# Tres clases distintas. Ninguna hereda de ModeloDeLenguaje:
# cumplen el contrato solo por tener el método con la misma forma.
class ModeloEnLaNube:
    def generar(self, prompt):
        ...   # aquí llamaría a la API de un proveedor; cuesta dinero y tarda

class ModeloLocal:
    def generar(self, prompt):
        ...   # aquí correría el modelo en tu propia máquina

class ModeloFalso:
    def generar(self, prompt):
        return "Resumen de prueba"   # respuesta fija: tests rápidos, sin red ni costo

# objeto que cumpla el contrato. La función nunca pregunta de qué clase es.
def resumir_ticket(ticket, modelo: ModeloDeLenguaje) -> str:

    # Aquí ocurre el polimorfismo: la llamada es siempre la misma y se
    # ejecuta el generar() del objeto que haya llegado.
    return modelo.generar(f"Resume este ticket de soporte: {ticket.texto}")

    # Intenta romper la cuenta con el primer botón, en ambos modos.
    class Cuenta:
    def __init__(self, saldo):
        self.__saldo = saldo          # doble guion bajo: Python lo oculta desde fuera

    @property
    def saldo(self):                  # se puede leer...
        return self.__saldo           # ...pero no hay setter: no se puede asignar

    def retirar(self, monto):         # la única puerta para cambiarlo

        self.__saldo -= monto
    Detalle de Python (lo preguntan)Python no tiene private real. _saldo es una convención que significa "no lo toques". __saldo activa el name mangling: Python lo renombra a _Cuenta__saldo, lo que dificulta el acceso pero no lo impide. En Java, C# o TypeScript el compilador sí lo prohíbe.
    Dilo así en la entrevista"Encapsular es proteger el estado: los datos solo cambian a través de métodos que hacen cumplir las reglas. Abstraer es simplificar el uso: expongo qué hace el objeto y oculto cómo. Una cuenta que valida los retiros encapsula; un método transferir() que esconde todo el proceso abstrae."

    Polimorfismo

    Un mismo llamado, muchos comportamientos. El código que llama no pregunta de qué tipo es el objeto.

    AnalogíaEl datáfono de una tienda. El cajero siempre hace lo mismo: "cobrar". Si pagas con tarjeta, QR o celular, cada medio resuelve el cobro a su manera. El cajero no cambia su rutina cuando aparece un medio de pago nuevo.
    Sin polimorfismo
    def checkout(tipo, monto):
    if tipo == "tarjeta":
        ...  # lógica de tarjeta
    elif tipo == "pse":
        ...  # lógica de PSE
    elif tipo == "nequi":
        ...  # lógica de Nequi
    # cada medio nuevo obliga
    # a abrir y editar esta función
    Con polimorfismo
    class Tarjeta:
    def procesar(self, monto): ...

class Pse:
    def procesar(self, monto): ...

class Nequi:
    def procesar(self, monto): ...

def checkout(pago, monto):
    return pago.procesar(monto)
    Pruébalo

    Ejecuta el mismo ciclo sobre todos los medios de pago. Después agrega uno nuevo y vuelve a ejecutar.

    Sobrecarga vs. sobrescritura

    Sobrecarga (overloading)Sobrescritura (overriding)
    Qué esVarios métodos con el mismo nombre y distintos parámetros, en la misma claseUna subclase redefine un método que heredó, con la misma firma
    Se decideAl compilar, según los argumentosAl ejecutar, según el tipo real del objeto
    Ejemplosumar(a, b) y sumar(a, b, c)CuentaAhorros.retirar() reemplaza a CuentaBancaria.retirar()
    En PythonNo existe: la segunda definición borra la primeraSí existe y es lo normal
    Detalle de PythonComo no hay sobrecarga, se usan parámetros con valor por defecto (def sumar(a, b, c=0)), *args o functools.singledispatch. TypeScript tampoco tiene sobrecarga real: sus "overloads" son solo firmas de tipos sobre una única implementación.

    Dos caminos al polimorfismo

    Por herencia

    Las clases comparten un padre y sobrescriben sus métodos.

    Tarjeta(MedioDePago), Pse(MedioDePago)

    Por interfaz

    Las clases no son familia; solo cumplen el mismo contrato.

    En Python basta con que tengan el método. Se llama duck typing, y se formaliza con Protocol.
    Dilo así en la entrevista"Polimorfismo es poder tratar objetos de tipos distintos a través de una misma interfaz, y que cada uno responda con su propia implementación. En un checkout, el servicio llama pago.procesar() sin saber si es tarjeta o PSE. La ventaja es que agrego un medio de pago creando una clase nueva, sin modificar el código que ya funciona."

    Clase abstracta vs. interfaz

    Las dos definen "lo que una clase debe tener". Una además trae código; la otra solo es un contrato.

    AnalogíaUna clase abstracta es una casa en obra gris: estructura y tuberías ya están hechas, tú terminas los acabados. Una interfaz es la norma del enchufe: no te da nada construido, solo exige que tu aparato encaje.
    Clase abstractaInterfaz
    Relación"Es un" (misma familia)"Puede hacer" (misma capacidad)
    Trae código y estadoSíNo, solo firmas
    Cuántas por claseUna sola en Java y C#Varias
    Se puede instanciarNoNo
    En PythonABC + @abstractmethodtyping.Protocol
    Clase abstracta: comparte código
    from abc import ABC, abstractmethod

class Reporte(ABC):
    def generar(self):          # código común
        return self.cabecera() + self.cuerpo()

    def cabecera(self):
        return "ACME S.A.\n"

    @abstractmethod
    def cuerpo(self): ...       # cada hijo lo define

class ReporteVentas(Reporte):
    def cuerpo(self):
        return "Ventas del mes"
    Interfaz: solo el contrato
    from typing import Protocol

class Exportable(Protocol):
    def exportar(self) -> str: ...

class Factura:                  # no hereda de nadie
    def exportar(self) -> str:
        return "factura.pdf"

def guardar(x: Exportable):
    print(x.exportar())

guardar(Factura())   # cumple por tener el método

    Practica: ¿cuál usarías?
    Dilo así en la entrevista"Uso una clase abstracta cuando las subclases son de la misma familia y comparten código o estado. Uso una interfaz cuando solo necesito garantizar una capacidad en clases que no tienen relación entre sí. Una clase puede cumplir muchas interfaces, pero normalmente hereda de una sola clase."

    Composición vs. herencia

    Herencia dice "es un". Composición dice "tiene un". Cuando dudes, arma el objeto con piezas.

    AnalogíaHeredar es como un tatuaje: queda fijo desde que naces como esa clase. Componer es como ponerte una chaqueta: te la cambias cuando el clima cambia. Un computador de escritorio tiene una tarjeta gráfica y la puedes reemplazar sin cambiar de computador.
    Herencia: rígida
    class Notificador:
    def enviar(self, msg): ...

class NotificadorEmail(Notificador): ...
class NotificadorSms(Notificador): ...

# ¿Y si quiero email Y sms?
class NotificadorEmailSms(Notificador): ...
# ...y así con cada combinación
    Composición: piezas
    class Notificador:
    def __init__(self, canales):
        self.canales = canales     # TIENE canales

    def enviar(self, msg):
        for canal in self.canales:
            canal.enviar(msg)

n = Notificador([Email(), Sms()])
# otra combinación = otra lista
    Pruébalo: la explosión de subclases

    Marca los canales que el negocio pide soportar, en cualquier combinación.

    Con herencia necesitas3 clases
    Con composición necesitas2 clases

    Por qué se prefiere la composición

    Menos acoplamiento

    Un cambio en la clase padre puede romper a todos los hijos. Una pieza solo depende del contrato.

    Cambia en ejecución

    Puedes reemplazar una pieza mientras el programa corre. La herencia queda fija al escribir el código.

    Fácil de probar

    En un test pasas una pieza falsa. Con herencia arrastras todo lo del padre.

    Sin jerarquías profundas

    Tres niveles de herencia ya son difíciles de seguir. Las piezas se quedan planas.

    Puente con AngularYa compones todos los días: un componente no hereda de HttpClient, lo recibe en el constructor. Eso es "tiene un".
    Practica: ¿"es un" o "tiene un"?
    Dilo así en la entrevista"Uso herencia solo cuando hay una relación 'es un' real y estable. En los demás casos compongo: la clase recibe objetos que hacen parte del trabajo. Así evito jerarquías frágiles, puedo cambiar comportamientos en ejecución y los tests son más simples."

    SOLID

    Cinco reglas para que el código aguante los cambios. En entrevista piden nombrarlas y explicar dos o tres. Las más pedidas son la S y la D.

    S: responsabilidad única

    Una clase debe tener una sola razón para cambiar.

    AnalogíaEn un restaurante el chef cocina, el mesero atiende y el cajero cobra. Si una sola persona hace todo, cualquier cambio en el menú afecta la caja.
    Mal: tres razones para cambiar

    Acoplamiento y cohesión

    La meta de casi todo lo anterior cabe en una frase: bajo acoplamiento y alta cohesión.

    Entre clases

    Acoplamiento

    Cuánto sabe una clase de las demás. Si cambiar A te obliga a cambiar B, C y D, están muy acopladas.

    Quieres que sea bajo.
    Dentro de una clase

    Cohesión

    Qué tan relacionado está todo lo que hay dentro. Si los métodos sirven al mismo propósito, hay alta cohesión.

    Quieres que sea alta.
    AnalogíaPiezas de Lego: cada una hace una sola cosa (alta cohesión) y se conecta con cualquier otra por un encaje estándar (bajo acoplamiento). Lo contrario es un mueble pegado con pegante: para cambiar una tabla rompes todo.

    calcular_ivaenviar_emailleer_csvvalidar_cedulaconectar_bdformatear_fecha
    Clase Utilidades: seis temas distintos, seis razones para cambiar.
    Alta cohesión: un propósito
    agregar_itemquitar_itemtotalaplicar_cuponvaciarcantidad
    Clase Carrito: todo gira alrededor del carrito.
    HerramientaQué mejora
    Responsabilidad única (S)Sube la cohesión
    Interfaces e inversión de dependencias (D)Baja el acoplamiento
    Composición e inyección de dependenciasBaja el acoplamiento
    EncapsulamientoBaja el acoplamiento: nadie depende de tus datos internos

    Lo de instancia pertenece a cada objeto. Lo estático pertenece a la clase y lo comparten todos.

    class Usuario:
    total = 0                      # atributo de clase: uno solo, compartido

    def __init__(self, nombre):
        self.nombre = nombre       # atributo de instancia: uno por objeto
        Usuario.total += 1

    def saludar(self):             # método de instancia: usa self
        return f"Hola, soy {self.nombre}"

    @classmethod
    def desde_email(cls, email):   # método de clase: recibe la clase, crea objetos
        return cls(email.split("@")[0])

    @staticmethod
    def es_email_valido(texto):    # método estático: no usa ni self ni cls
        return "@" in texto
